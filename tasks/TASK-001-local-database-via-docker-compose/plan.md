## Business goal reference

See `task.md` for the business problem, desired outcome, and acceptance
criteria. This plan must not change the original business goal.

Goal: a developer can start a local database with one documented Docker Compose
command, without installing or configuring a database server manually, and the
database is ready to be used by the backend application in follow-up tasks.

## Proposed solution

Define a single PostgreSQL 17 service in a Compose v2 file, run it with
`docker compose up -d`, persist its data in a named Docker volume, and supply
credentials through environment variables read from a local `.env` file that is
git-ignored, with a committed non-secret `.env.example` as the template.
Document start, verify, stop, cleanup, data location, and restart behavior.

Rationale: PostgreSQL is the most common pairing for a Next.js/TypeScript
backend and is required by later backend tasks; the official image avoids
custom build work; a named volume survives restarts without polluting the
repository; env-based credentials satisfy the "no committed secrets" criterion.

## Architecture and data flow

```
developer machine
  |-- docker compose up -d
  |     `-- service: db  (image postgres:17)
  |           |-- env: POSTGRES_USER / POSTGRES_PASSWORD / POSTGRES_DB  <- .env
  |           |-- port: 5432 -> container 5432
  |           |-- volume: pgdata -> /var/lib/postgresql/data
  |           `-- healthcheck: pg_isready
  `-- future backend app (later task) connects to localhost:5432
```

No application code path is involved in this task; the database is standalone
until a follow-up integration task.

## Data and API changes

- Data model / API: none (no schema, no endpoints).
- Configuration (new environment variables, documented in `.env.example`):
  - `POSTGRES_USER` (default `educator`)
  - `POSTGRES_PASSWORD` (default `educator_local_pw`; local-only, non-secret
    placeholder that must be changed for anything non-local)
  - `POSTGRES_DB` (default `educator`)
  - `POSTGRES_PORT` (default `5432`, host mapping)
- Dependencies: none added to `package.json`. The only external dependency is
  the Docker image `postgres:17`.

Proposed `compose.yaml` shape (Compose v2, no `version:` key):

```yaml
services:
  db:
    image: postgres:17
    restart: unless-stopped
    environment:
      POSTGRES_USER: ${POSTGRES_USER:-educator}
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD:-educator_local_pw}
      POSTGRES_DB: ${POSTGRES_DB:-educator}
    ports:
      - "127.0.0.1:${POSTGRES_PORT:-5432}:5432"
    volumes:
      - pgdata:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U ${POSTGRES_USER:-educator} -d ${POSTGRES_DB:-educator}"]
      interval: 5s
      timeout: 5s
      retries: 10
      start_period: 30s

volumes:
  pgdata:
```

The port is bound to `127.0.0.1` so the database is reachable only from the
local machine. No fixed `container_name` is set, so Compose names the container
`<project>-<service>-1` (e.g. `educator-db-1`) and two checkouts on one host can
coexist.

Compose automatically reads `.env` in the project directory for these
substitutions; the inline defaults keep startup working even if `.env` is
absent (the developer still copies `.env.example` for a clean, documented
setup).

## Testing strategy

No test framework is configured, so verification is a documented manual
checklist executed against the real service. Each step yields evidence.

Start:

```
cp .env.example .env
docker compose up -d
docker compose ps          # expect db "healthy"
```

Reachability from the local machine (works without a host `psql`):

```
docker run --rm --network host postgres:17 \
  psql "postgresql://educator:educator_local_pw@127.0.0.1:5432/educator" -c "select 1;"
```

Alternative, if a host `psql` exists:
`psql -h 127.0.0.1 -p 5432 -U educator -d educator -c "select 1;"`.

Inside-container checks:

```
docker compose exec db pg_isready -U educator -d educator
docker compose exec db psql -U educator -d educator -c "select version();"
```

Persistence across restart:

```
docker compose exec db psql -U educator -d educator -c "create table t_persist(id int);"
docker compose restart
docker compose exec db psql -U educator -d educator -c "select to_regclass('public.t_persist');"
docker compose exec db psql -U educator -d educator -c "drop table t_persist;"
```

Stop / cleanup:

```
docker compose down        # stops, keeps data
docker compose down -v     # stops and deletes the pgdata volume
```

Reproducibility (AC5): the docs describe the from-scratch path (clone, copy
`.env.example` to `.env`, `docker compose up -d`, run the verify command). This
criterion is inherently a human/second-machine check and is verified by the
reviewer following only the docs on a clean checkout.

## Security and failure handling

- Secrets: only non-secret local placeholders are committed in `.env.example`;
  the real `.env` is ignored (`.env*` plus the intended `!.env.example`
  negation). The docs must warn that `.env` must never be committed and that
  the default password is for local use only. This placeholder interpretation
  of AC7 was explicitly confirmed by the user (review finding R6).
- Network exposure: the port is published on loopback only
  (`127.0.0.1:...:5432`), so even with the known default password the database
  is not reachable from other hosts (review finding R1).
- Validation: Compose fails fast if the image cannot be pulled; the healthcheck
  gates readiness so "started" is distinguishable from "accepting
  connections".
- Failure handling: a port conflict on 5432 is the most likely failure; the
  docs must explain how to change `POSTGRES_PORT`. A data-directory mismatch is
  avoided by pinning PostgreSQL 17 (PostgreSQL 18 changed the default data
  directory).
- Compatibility: Compose v2 file format (`compose.yaml`, no `version:` key),
  matching the installed `docker compose` v2. Legacy `docker-compose` is not a
  requirement.

## Risks and alternatives

Risks:

- Host port 5432 may already be in use (existing local Postgres). Mitigation:
  documented `POSTGRES_PORT` override.
- Forgetting the `.gitignore` exception would either block committing
  `.env.example` or risk committing `.env`. Mitigation: explicit step 2 and a
  `git status` check in step 9.
- Compose project-name collisions could reuse an unrelated volume named
  `pgdata`. Mitigation: the volume is namespaced by the Compose project name
  (`<project>_pgdata`), and no fixed `container_name` is set so the container is
  also namespaced (`<project>-<service>-1`). `COMPOSE_PROJECT_NAME` can be set to control
  the project name. (Corrected in draft-2: a fixed `container_name` would have
  defeated this.)
- "A second developer reaches the same result" cannot be fully automated and
  depends on their Docker being installed. Mitigation: precise prerequisites in
  the docs.

Alternatives considered:

- MySQL 8 instead of PostgreSQL 17 — rejected (the team chose PostgreSQL).
- Bind-mount `./data` instead of a named volume — rejected (risk of accidental
  commits; a named volume is cleaner).
- Legacy `docker-compose` — rejected (not installed; v2 is the current
  standard).
- Bundling Adminer/pgAdmin — rejected as out of scope; can be a later task.
- Inline credentials only, no `.env` — rejected in favour of an example plus a
  local file for clearer onboarding.

Rollback: `docker compose down -v` removes the container, volume, and data;
deleting `compose.yaml`, `.env.example`, and the documented files fully reverts
the change. No application code is affected.
